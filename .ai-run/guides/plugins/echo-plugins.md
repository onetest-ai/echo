# Echo Plugins

**Project**: Echo · **Stack**: Rust (+ vanilla JavaScript window UI, TypeScript status-line mod), tao + wry + tray-icon, clap, rquickjs · **Scope**: the rules for Echo's side of plugins: capabilities, host services, grants, client-half ctx and slots, widget kinds, scripts, marketplaces

What Echo's side does today — the store's files and locks, script runs, sessions, the `.plugins` layout, dashboards —
is the reference `.ai-run/reference/plugins/echo-host.md` ("Host § <section>" below); the API plugins see is
`.ai-run/reference/plugins/plugin-api.md` ("API § <section>"). A change to either goes with the code it describes.

## Plugin host

### Rules
- R1. Add a capability plugins may ask for as a `Capability` in `plugins::CAPABILITIES` with its own `describe` writing the sheet's words in Echo, never the plugin's; keep `ready: false` until the host implements it. Evidence: `plugins::CAPABILITIES`
- R2. Add a host-half service in two places: the `ctx` object in `jshost::PRELUDE`, then an arm in `jshost::service` (returns at once) or `jshost::service_async` (spawns a process, waits on the network or a dialog). Evidence: `jshost::PRELUDE`
- R3. A host service that reaches Echo data, granted folders, sessions or the network checks the manifest first with `jshost::uses` / `jshost::uses_flag` or the capability's own list (`network.hosts`, `network.ask`, `network.web`, `speech`, `channel.plugin`, `deliver_provider.kinds`, `signin.hosts`, `m365.read`, `microphone`). Evidence: `jshost::uses_flag`, `plugins::may_use_signin`
- R4. Resolve a plugin's own files with `plugins::inside_plugin` / `inside_plugin_dir`, its store with `jshost::store_path`, granted folders with `grants::resolve` (reads) and `grants::writable` (writes: never a link, the deepest existing folder inside the root), and other apps' files only as named in `uses.files.read` (`plugins::app_file`); each refuses absolute paths and `..`. A write reaches a hidden path only as `grants::hidden_ok` lists it (`.gitignore`, `.obsidian/<name>.json` but the plugin lists, `.claude/skills/<name>/*.md`, written whole) — a skill only with content `claude_skills::skill_md_ok` passes (no hooks, tool grants or commands); never Claude Code's settings, hooks, agents or commands, git's own files or an Obsidian plugin. Evidence: `plugins::inside_plugin`
- R5. Validate a manifest only in `plugins::read_manifest`; a new manifest field gets its check there. Evidence: `plugins::read_manifest`
- R6. A host half's command or tick that runs JavaScript for over 5 s is interrupted (`jshost::SLICE`); move bulk file work to the async services (`ctx.fs.readMany`, `ctx.fs.walk`, `ctx.fs.search`, `ctx.fs.snapshot`, `ctx.fs.copyIn`), which run off the slice. Evidence: `jshost::SLICE`
- R7. Add a client-half slot by listing it in `SLOTS` (window script) and drawing it with `slotItems` — a slot of rows its own way, each plugin's row drawn on its own (`thread.profile`, `client.profile`, `call.header`, `call.minutes`: `threadSlotRows`, `threadSlotAfter`); register everything a plugin adds under its id so `unloadPlugin` takes it out. Evidence: `unloadPlugin` (window script)
- R8. A new `ctx.echo.read` kind goes in `plugins::ECHO_READS` (the sheet's words) and the `echo.read` arm of `jshost::service`, its data from `share.rs`; an unknown kind is named on the sheet and granted nothing. Evidence: `plugins::ECHO_READS`
- R9. A plugin's Claude runs only through `claudejob::run` on one of the user's AI profiles, with search narrowed to it; never a plugin's own key or account, nor a program of its own as Claude Code. A run in a folder the user granted it is that folder's own project with Echo's session as a routine has it; `read` changes nothing in the folder, `edit` (only with `folders.write`) and `copy` (on a snapshot) get every tool. A run in a folder of its own store gets the same session and every tool, but no project: nothing in the store loads as Claude Code's settings, hooks or skills, and Echo tells it the files are data. Its permissions are the plugin's `tools` (skip only as its sheet allows), else the user's setting for routines. An interactive session a plugin opens on the user's click (`ctx.claude.session`) is the user's: the same folder project, tools and builder, its permissions from the folder session's setting, and the plugin's `ctx` neither types into it nor reads it. Evidence: `claudejob::run`, `terminal::start_plugin`
- R10. A plugin's session skills (its runtime text skills and its package skills) go only to Echo's sessions, never to the user's own Claude Code (Host § Sessions). The one exception: a skill the plugin adds to the user's own Claude Code with `ctx.claude.installSkill` — `uses.skills` on its sheet, only on the user's click, only `skills/<name>/SKILL.md` that `skill_md_ok` passes, never over a skill it didn't add, and gone with the plugin (`plugins::claude_skills`). Evidence: `grants::set_session_skills`, `folder_args::build`
- R11. Never let a channel's env set a `CLAUDE*` or `ANTHROPIC*` key. Evidence: `jshost::service`
- R12. Deliver only to the user and the addresses the user set on a routine, never to an address a model picked; anything a model wrote carries `ai_notice`. Evidence: `deliver::send`
- R13. Add a kind of plugin widget in three places: `plugins::WIDGET_KINDS`, its drawing in `pluginWidgetHtml` (the window script: every text through `esc`, a link only where API § Open, actions and links lets it go, data it can't draw throws with what is wrong), and its cases in `today-plugin-widgets.test.mjs`; a plugin's widget data is read from its last answer, never by waiting on the plugin while Today draws. Evidence: `widgets::plugin_data`
- R14. Echo's own files in a plugin's store (Host § Store) change only through Echo's services, each under its own lock across processes, and the plugin can neither write nor remove them; Echo removes nothing else of the store but what it sweeps (`cache/`, its `.part` downloads). A marketplace namespace's shared values are no plugin's store and never removed with one. Evidence: `jshost::sweep_store`, `jshost::not_echos`
- R15. Echo's sessions run a plugin's commands only as its manifest names them in `uses.sessions.commands` (the sheet says so); no other `plugin call` (Host § Sessions). Evidence: `plugins::session_commands`
- R16. A plugin's package skills reach Echo's sessions only as Echo copies them from the installed package, checked as API § Claude in Echo sets them; the host half can neither write nor remove them (Host § Sessions). Evidence: `grants::copy_package_skills`
- R17. Echo runs a plugin's script only as `uses.scripts` names it, never through a shell, its arguments as plain words, every run through `plugins::scripts::run` (Host § Script runs). Evidence: `plugins::scripts::run`
- R18. A script runs isolated: no stdin, in its own process group killed whole when its time is up or its plugin goes, its output capped, one run of a script at a time across processes, and without Echo's secrets or any `CLAUDE*` / `ANTHROPIC*` key in its environment (Host § Script runs, API § Scripts). Evidence: `plugins::scripts::run`, `plugins::scripts::stop_plugin`
- R19. The sheet names each script and what it may do, and an update that adds a script or changes any file of a skill folder that has one asks again (API § `uses` and the permission sheet). Evidence: `plugins::scripts::describe_scripts`, `plugins::scripts::check`
- R20. A dashboard fills its widgets' `thread` / `client` settings itself and offers only the widgets that have them; each place a widget is on is asked, and its answer kept, on its own (Host § Dashboards). Evidence: `today_layout::params_on`, `today_layout::Page::holds_thread`
- R21. Plugins reach Claude in Echo only through what Echo lays out at `.plugins/<id>/` and one line each in Echo's core; guarded runs never write under `.plugins/`, and the sessions' pre-tool hook refuses writes there (Host § Layout). Evidence: `plugins::agent::lay_out`, `guard`
- R22. A plugin changes a thread only through `projects::plugin_set_stage` and `ledger::plugin_upsert` / `plugin_close`, as `uses.echo.write` names: only its own tasks, by its key; never a field or task the user set, nor a stage the user changed away from its own until they hand it back; its name and reason in the history; a proposal only on the user's Yes, and the same one after their No stays quiet; refused in a run scoped to another thread. Evidence: `ledger::plugin_upsert`, `projects::stage_held_from` A plugin keeps only its own values per client (`plugins::client_values`), never a client field Echo or the user set.
- R23. A plugin's dashboard (its manifest's `dashboards`) is only offered; the user adds it, and Echo never adds, changes or removes a dashboard by itself: a plugin's update that changed it is said on it and taken only on the user's Update; with its plugin off or removed it stays the user's. Its widgets are the plugin's own or its marketplace's, never set to the page's thread or client. Evidence: `boards::add_preset`, `boards::take_update`, `plugins::presets::check`
- R24. A plugin offers a wrapper profile (claude-code-runs R12, R13) only as `uses.ai.wrapper` names it: a name and a command that is one program name (letters, digits, `.`, `_`, `-`) with no arguments, never a file of the plugin. The sheet names the command and says that it sees and can change everything Claude in Echo is sent, call transcripts included. Echo offers it in AI profiles and only the user adds it; an update that changes the command is offered on the profile and taken only on the user's yes; the plugin off or removed leaves the profile the user added. Evidence: `plugins::read_manifest`, `ai::offered`
- R25. A plugin sees and tunes Echo's background jobs only as `uses.echo.jobs` names it; its sheet says it shows them and can change how often each runs, when it pauses and which model it uses. It reads them only through `jobs::list`, `jobs::routines` and their runs (`jobs::runs`, `jobs::routine_runs`), whose words are Echo's own and counts — never a call's, thread's or person's name, nor a model's text — and changes them only through `jobs::set`, checked as `echoctl jobs set` is; a change comes only from its client half on the user's own click or key in its UI, never from its host half, a run Echo started, a schedule or an event. Echo's jobs run on their own settings with or without the plugin, and removing it changes none of them. Its own routines (R29) it may tune the same way but never switch on or off. Evidence: `jobs::set`, `jobs::routines`
- R26. A file the user hands a plugin (picked, dropped, or named by `--file`) reaches it only as a handle of its own, never a path: it reads it through `ctx.files.read` and puts its bytes into a granted folder only through `ctx.fs.copyIn`; another plugin's handle is no handle, and a plugin's handles go when it is switched off, updated or removed. Evidence: `jshost::files`
- R27. Echo runs git for a plugin only through `ctx.git` (`jshost::git`): a fixed list of verbs, no shell, literal paths, and the repository's own settings, hooks and includes run nothing — a repository whose layout or settings a plugin could write, or that points elsewhere, is refused. Evidence: `jshost::git`
- R28. A plugin's microphone opens only as `uses.microphone` names it, on the user's click in its view, one grant for that opening, with Echo's sign showing while it is open, and never while Echo records; the window grants no other capture. Evidence: `window::plugins::mic_open`
- R29. A plugin's routines are named on its sheet (its manifest's `routines`, the prompt a file of its package) and stay off until the user switches each on; they run as routines through `claudejob::run` under the routines' permission setting, their state and runs kept with Echo's jobs in Echo's own words; an update the user agreed to keeps an on routine on, a new one starts off, removing the plugin switches them off. Evidence: `plugins::routines`, `jobs::routines`
- R30. A plugin reads the public web only under `uses.network.web`, whose sheet line says it can send what it knows to any site through the addresses it opens; it never reaches this computer or the user's own network that way. Evidence: `jshost::web::web_reach`, `plugins::capabilities::WEB_LINE`
- R31. A page rendered for a plugin (`ctx.web.read({render: true})`) only under `uses.network.web`, in a short-lived process apart from the window, its IPC and the plugin's `ctx`: every request it makes goes through Echo's check of public addresses, nothing it stores outlives the render, and it opens no download, popup, permission or file. Evidence: `jshost::web::render` (#835)

### Constraints
| Do not | Do instead | Evidence |
|---|---|---|
| Put a link or special file in a plugin or marketplace tree | Ship plain files within the tree limits (API § Package and manifest) | `plugins::check_tree` |
| Fetch from or connect to a host neither the manifest names nor the user listed or typed | `ctx.http.fetch` / `ctx.http.stream` to `https://` hosts listed in `uses.network.hosts`, or — and `ctx.net.websocket` only — to what the addresses the user listed in a setting named by `uses.network.hosts_from` match (plain http too; outside their own network its row says anyone on the way can read it); a page the user typed in Echo's own dialog (`network.ask`), once, by GET; a public page read by `ctx.web.read` may have Echo fetch its own pictures from any public host — every resolved address public, ports 80/443, image types only, within the reader's caps — never a private one; with `uses.network.web`, `ctx.web.read` / `ctx.web.fetch` of any public https page by GET (ports 80/443, every resolved address public and the connection pinned to the address checked, each redirect checked again, at most 5, and once a page on the way was public every later one public too), never `ctx.http.fetch` | `jshost::fetch`, `jshost::net`, `jshost::web::web_reach`, `plugins::addresses` |
| Let a plugin trust a certificate | Only the user trusts a listed address's key, in the window or the CLI; Echo keeps pins outside the plugin's store | `plugins::pins` |
| Open the window to a host any other way | The window's `connect-src` / `media-src` add only the addresses the user listed for enabled plugins, each checked again where the policy is built | `window_csp` |
| Let a plugin set the addresses it may reach (`ctx.settings.set`, its `settings.json`, a manifest `default`) | Only the user enters them, in the window or the CLI; Echo keeps them outside the plugin's store | `plugins::listed_addresses` |
| Serve a plugin's store to the window beyond audio and pictures | `/plugin/<id>/store/<file>`, media kinds only, kept inside the store | `window::plugins::store_file` |
| Let a plugin write a runtime skill's frontmatter or hooks | Runtime text: pass `[{name, description, body}]` to `ctx.sessions.skills`, Echo writes the plugin around them; fixed text and scripts: a package skill (R16) | `grants::set_session_skills` |
| Let a plugin start a program any other way (a shell line, a path it builds, a file in its store) | A script it ships, named in `uses.scripts`, run from the copied folder | `plugins::scripts::run` |
